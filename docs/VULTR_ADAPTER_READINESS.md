# Vultr App Cloud adapter — offline slice and live gate

`VultrAdapter` is registered in `modules/addons/cloudhost247apps/providers/bootstrap.php`, but registration **does not turn on customer provisioning**. Both `customer_server_provisioning_enabled` and `customer_server_self_service_enabled` remain off by default. The adapter and worker flow are tested with scripted HTTP responses in suite `19_VultrAdapterTest.php`; **no live Vultr call, billable deployment, WHMCS/MySQL staging test or production validation is claimed**.

## Implemented and intentionally unavailable

Supported: authenticated account/SSH-key preflight; one Cloud Compute (`vc2`) instance create (201/202 accepted), read, 204/404 delete, 204 reboot/start/halt. A created or unhealthy instance remains `initializing` and is polled until the provider reports `active`, `power_status=running`, `server_status=ok` and a routable provider IPv4/IPv6 passes the worker's readiness gate. Placeholder `0.0.0.0` is never presented as an address. Rebuild, resize, snapshots and metrics are **not advertised**, and their methods fail before HTTP.

Create requires an operator-approved `public_config: {"plan_id":"vc2-...", "ssh_key_id":"<account SSH key UUID>"}` and encrypted `credentials: {"api_token":"..."}`. These values are examples, not a default plan or key. The product mapping's `image` is a *decimal Vultr OS ID*, checked against Vultr's paginated `/os` catalog; this slice allows only x64 Ubuntu/Debian, not app/snapshot/Windows images. The selected provider plan must exactly match the approved vCPU/RAM/disk, report availability in the mapped region in both `/plans` and `/regions/{region}/availability`, and have one disk when a disk count is reported. Different plan sizes require separate provider-account configurations. The adapter confirms the configured SSH key with `/ssh-keys/{id}`. It explicitly disables extra-charge backups and DDoS protection. The API may still return a generated `default_password` despite an SSH key being installed: the adapter **discards it** and redacts entire provider responses in HTTP traces; it cannot assert the guest disables password login. Check guest OS security separately in staging.

A deterministic `ch247-<sha256(key)[:32]>` tag permits recovery *when already visible* in `GET /instances?tag=...`. Cursor pagination is bounded and complete before trusting absence/uniqueness; cursor tokens are URL-encoded data for a fixed HTTPS API endpoint, never followed as URLs. A tagged instance must match the approved hostname, label, region, plan and OS ID. Vultr tags are **not** an atomic idempotency guarantee. Concurrent creates or delayed tag visibility may cause duplicate billing. Keep the existing per-server worker serialization and do not make parallel direct adapter calls. A lost/malformed/bad-status create response is terminal (`PROVIDER_CREATE_UNCERTAIN`) for automatic retries. Before any manual retry, inspect the Vultr account for matching/late instances and reconcile local service state and billing. A momentarily empty tag listing is not proof that a timed-out create failed. Ambiguous action POSTs are likewise terminal (`PROVIDER_ACTION_UNCERTAIN`).

## Live staging still required

Use an isolated account and approved billing budget. Verify the token's provisioning ACL and API IP allowlist, SSH key ownership/injection and guest authentication, accepted create status and tag visibility timing, OS/plan/region availability, real status and network fields, 204 action semantics, deletion/replay, cursor pagination, rate limits, create timeouts **after acceptance**, and orphan/duplicate reconciliation. Then test WHMCS paid/unpaid ownership and mapping revocation on the target release/database. Record evidence and operator approval before changing either provisioning switch. This offline adapter is **not** a claim of operational readiness.

Provider references used: [official Vultr Go API client](https://github.com/vultr/govultr) (current `instance.go`, `plan.go`, `os.go`, `ssh_key.go`, `region.go`, `listOptions.go`) and [Vultr API Postman OpenAPI schema](https://github.com/vultr/api-postman-collection/blob/master/postman/schemas/schema.json). The older schema documents a singular `tag` and 202; current official clients use `tags[]`, and both 201 and 202 are handled. Confirm live behavior in staging.
