# Contabo App Cloud — existing-instance adoption only

**Chosen ownership model:** the operator links an **already-paid, already-owned** Contabo instance to an active WHMCS service. App Cloud **never purchases or cancels** a Contabo contract. `ContaboReadOnlyAdapter` is registered with **only `server.get: true`**; `server.create`, delete, power, rebuild, resize, snapshots and metrics are unavailable and fail before provider I/O. This read-only registration does **not** make Contabo orderable through `/v1/servers` or the customer self-service cart. Its separate `contabo_adoption_enabled` switch defaults **off**. No live Contabo credential or WHMCS/MySQL staging evidence is available here.

## Why it is separate from customer VPS provisioning

Contabo's [official API documentation](https://api.contabo.com/#tag/Instances) describes `POST /v1/compute/instances` as creating a **new provider contract** with required initial `period` in months, `productId` and region. An existing paid WHMCS invoice is not authorization for a second Contabo order. `POST /v1/compute/instances/{instanceId}/cancel` schedules a `cancelDate`; it is **not** immediate VM deletion. Its `x-request-id` is documented as a support-case request identifier, not a provider-enforced idempotency key. These endpoints are **never called** by the adoption path.

The existing `customer_servers` table and action endpoints are for App Cloud-created VMs. Adoption instead has an additive `contabo_adoptions` table (migration `0013`) with unique WHMCS service and provider-account/instance bindings. Adopted records are **operator-only** and are not represented as customer-active VMs or exposed in `/v1/servers`; this avoids silently transferring billing, renewal or cancellation ownership. A WHMCS service already reserved for adoption cannot also queue an App Cloud VM create. A WHMCS product already assigned to a provisioning module remains ineligible for App Cloud's self-service create mapping, but a product whose existing owner is `contabo` may be adopted without invoking that module's create function.

## Operator workflow (offline-tested, live gate still required)

1. Upgrade App Cloud to **1.11.0** and apply migration `0013`. In the encrypted provider-account vault, configure `provider_code: "contabo"`, `credentials: {"client_id":"...", "client_secret":"...", "username":"...", "password":"..."}` and non-secret `public_config: {"tenant_id":"DE", "customer_id":"<provider customer ID>"}`. No credential belongs in Git or a public-config field. Queue account verification; the worker obtains an OAuth token at the **fixed HTTPS** Contabo auth URL, then performs a paginated-list permission check against the **fixed HTTPS** API URL. Both responses are fully redacted from traces. Verification does *not* prove ownership of a particular instance; the adoption read must also match its tenant and customer IDs.
2. After an isolated staging review, an operator may enable **only** `contabo_adoption_enabled`. Leave the separate create/self-service switches off unless their **other** providers' gates pass. A staff administrator with both `customer_server.manage` and `provider_account.manage` (and matching bearer-token scopes when applicable) sends a CSRF-protected `POST /v1/contabo/adoptions` with `Idempotency-Key` and JSON, using **real** values rather than these examples:

   ```json
   {"service_id":456,"provider_account_id":4,"provider_instance_id":"12345","contabo_product_id":"V153","spec":{"region":"EU","image":"9b1deb4d-3b7d-4bad-9bdd-2b0d7b3dcb6d","cpu_cores":2,"memory_mb":4096,"storage_gb":100},"acknowledge_existing_contract":true}
   ```

   WHMCS must confirm the service is **active**, its order and invoice belong to the same client, and that invoice is paid. The WHMCS product must be a recurring server product without an App Cloud create mapping and with no other server module except `contabo`. Neither the customer nor the browser can choose a provider ID on a customer-facing route. The request reserves the service and instance uniquely and queues **only a provider read** in the provisioning worker; it does not claim verification or customer activation on HTTP success.
3. The worker rechecks payment, service/product and account status before and after the Contabo read. It compares provider instance ID, account tenant/customer IDs, Linux OS, provider product ID, region, image, vCPU/RAM/disk and usable status to the operator-approved envelope. A running instance must have a provider IP. A mismatch fails the adoption without binding or changing any provider contract; a new idempotency key can explicitly retry the **same** failed binding after remediation. `GET /v1/contabo/adoptions` and `GET /v1/contabo/adoptions/{id}` are staff-only; there is no customer adopt endpoint or provider-action endpoint.

## Remaining live gate

Verify the OAuth password-grant response, token expiry, account scoping, secret redaction, instance response units and statuses, provider product ownership and WHMCS billing/renewal authority against a **real isolated account** and the target WHMCS/MySQL release. Confirm that the operator-provided instance belongs to the paid service (the API can confirm Contabo account ownership, not the business relationship between Contabo and a WHMCS invoice). Validate WHMCS Contabo module naming, owner transfer, cancellations and adoption correction/removal procedures. Only then enable adoption. This checkout makes **no** claim of live provider readiness, customer-visible adopted VPSes, automatic refresh, or Contabo purchase/cancel support.

Offline tests: `modules/addons/cloudhost247apps/tests/20_ContaboReadinessTest.php`. They simulate OAuth, provider read-back, WHMCS payment/active-service checks, RBAC/CSRF, unique reservations, transient read backoff, mismatch, explicit retry, and no purchase/cancel calls. The Contabo suite also passes under the PHP 7.4 WebAssembly runtime; this does not substitute for WHMCS/MySQL staging.
