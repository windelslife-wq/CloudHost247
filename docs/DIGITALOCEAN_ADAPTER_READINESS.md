# DigitalOcean App Cloud adapter — offline slice and staging gate

`DigitalOceanAdapter` is registered in `modules/addons/cloudhost247apps/providers/bootstrap.php`. It uses the fixed `https://api.digitalocean.com/v2` endpoint with verified TLS, bounded responses and redacted HTTP traces. **Registration does not enable customer provisioning**: `customer_server_provisioning_enabled` and `customer_server_self_service_enabled` remain off by default. Suite `18_DigitalOceanAdapterTest.php` uses a scripted HTTP fake, including an account-verification → paid-service create → asynchronous poll → readiness-gate activation path. No live DigitalOcean credential, paid Droplet, WHMCS/MySQL staging run or production validation is claimed.

## Supported and deliberately unsupported

Supported: verify an active account and its pre-existing SSH key; create a single Droplet; read and delete it (204/404); reboot, power on, power off (201 action ID). The 202 create response is *accepted*, not *ready*; a later worker poll checks the provider's state and public network address before activation. Only the provider's public IPv4/IPv6 interfaces are returned. Rebuild, resize, snapshots and metrics are **not advertised** and fail closed without a provider call. The customer API still enforces per-capability gates, WHMCS payment/ownership and operator mapping.

## Operator configuration

- Configure a provider account with `provider_code: "digitalocean"`, a `region` that matches the product mapping, encrypted `credentials: {"api_token": "..."}`, and `public_config: {"size_slug": "s-2vcpu-2gb", "ssh_key_id": "123"}`. The example size/key are placeholders, **not** defaults; use a real non-GPU size slug and an SSH key ID already registered with that team. Never put the API token or private SSH key in `public_config` or Git. Keep the account unverified/disabled until the queued verification succeeds. Separate size slugs require separate provider-account configurations. Rotate credentials through the provider-account vault.
- Grant a restricted token the scopes required by the official API endpoints: `account:read`, `ssh_key:read`, `droplet:read`, `droplet:create`, `droplet:delete`, `droplet:update`, `sizes:read`, `regions:read`, `image:read`, `tag:create`, `tag:read`. Confirm the actual scope set in staging. The product's `image` must be a valid public image slug; its exact vCPU/RAM/disk and region must match the configured slug in the provider-sourced paginated `/sizes` catalog. No guessed size, password authentication, optional paid backups, GPU Droplets or unapproved customer-supplied size is used.
- A deterministic `ch247-<sha256(key)[:32]>` tag is used to find an existing Droplet before POST. The adapter verifies that any tagged resource also matches the mapped name, image, size and region and fails on multiple matches or incomplete pagination. It never follows a provider-supplied next URL. **Tags are not a provider-enforced atomic idempotency key.** Concurrent creates or eventual tag visibility cannot be guaranteed safe by the remote API. Keep one supervised worker per provisioned resource, and do not invoke the adapter directly in parallel.
- A lost/invalid create response, 5xx or transport timeout is **terminal for automatic create retries** (`PROVIDER_CREATE_UNCERTAIN`). It may have incurred a billable Droplet. Before *any* manual retry or new request, an operator must inspect the DigitalOcean account for the deterministic tag and matching VM, reconcile the local service/VM and billing, and remove any duplicates safely. A tag lookup that finds nothing immediately after an ambiguous result is **not** proof of absence. Action POSTs are also terminal on ambiguous outcomes. Other read/preflight failures can retry normally. Never turn on automated external retries for ambiguous POSTs without a provider-backed idempotency design.

## Live gate (not completed here)

On an isolated test account, confirm token scopes and SSH key ownership, catalog exactness and pricing, image/region availability, 202 → active transition and public IP, poll/readiness behavior, action semantics, 204 deletion, repeated requests, 429/5xx/timeouts (especially after an accepted POST), tag visibility delay and concurrent worker behavior. Reconcile orphan/duplicate handling with operations, then test paid/unpaid WHMCS services, mapping revocation and database upgrades before enabling either provisioning switch. Record the evidence and an operator sign-off; offline fake tests alone are not production readiness.

API reference used for the implementation: [DigitalOcean OpenAPI](https://github.com/digitalocean/openapi) (`specification/resources/droplets`, `sizes`, `ssh_keys`, `account`).
